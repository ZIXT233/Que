# ACP 生命周期审查（2026-09-27）

范围：聊天组件、HTTP/Rust 桥接、Node owner、acpx 存储。以下结论来自源码及隔离故障测试，不代表全部 Harness 或真实 SSH 网络已经验收。

## 已确认并修复

| 严重性 | 原问题 | 修复及证据 |
| --- | --- | --- |
| 高 | 聊天快照、发送状态属于 React 组件实例；卡片从牌堆移到查看视图后重建，表现为重新加载，也会丢失发送收据 | 同一 WebView 按卡片、工作区、目录及 Harness 保留状态；初次读取历史与启动连接分开。组件重挂载、发送中移动卡片测试 |
| 高 | 流事件和 RPC 响应都能覆盖快照，缺少先后顺序；成功发送前发起的读请求，失败后还能把成功状态改回异常 | owner 启动标识及递增版本，Rust 丢弃旧版本；前端控制操作前后推进请求版本，对成功和失败都校验。Rust 乱序测试、前端旧失败回归 |
| 高 | 排队请求尚未进入 acpx 历史时，收据没有正文；重启后变为空消息。撤回标志和错误原因也没有完整保留 | 只有尚未得到 acpx messageId 的收据暂存待提交正文/附件；确认 acpx 保存成功后去掉待提交副本。历史仍由 acpx 管理。SIGKILL 后恢复、撤回不复活、重复请求不重执行测试 |
| 高 | 网络/HTTP 失败被直接转换为任务结束状态，混淆“看不到执行”与“没有执行”；HTTP 取消还可能遗留 RPC 等待者 | 断链保留最后观察到的 turn 状态，只更新连接异常；RPC 等待者使用析构清理。断链及等待者测试 |
| 高 | 发送成功后还要求额外 GET 成功，GET 超时会把已接收消息显示为发送失败；重挂载/刷新可能失去重试 ID | POST 接收结果直接更新消息；同一不确定请求使用相同 ID 重试，sessionStorage 仅保存 ID 和内容哈希，不保存另一份聊天历史。接收、丢回执、重挂载和哈希收据测试 |
| 中 | 每次启动轻量 relay 都读取所有历史；每次只读查询又重建完整历史，增加延迟并可能与启动交错 | relay 只转发；只有 owner 启动加载历史，读取内存快照不改写历史。真实 acpx fixture 生命周期测试 |
| 中 | 同时存在多个权限请求时，答复一个就标为 working | 仍有待答复请求时保留 attention |
| 高 | 绑定存在而 acpx 记录缺失时，有机会静默创建替代会话 | 有未完成收据的缺失记录明确报错，保留绑定，不用空会话伪装恢复成功 |

## 状态约束

- 历史未加载、连接正在建立、消息等待接收、任务排队/执行、请求控制操作是不同维度。
- UI 位置不是会话身份，移动卡片不改变请求 ID。
- `send` 返回 Turn，其他配置/读取通常返回 Snapshot，调用方不能混用。
- 连接中断不证明任务结束。只有 owner 的结果或 owner 进程重启的恢复过程能改变 turn 的终结状态。
- 超时/崩溃之后不自动重放不确定任务；按相同请求 ID 查询/重试只拿回原收据。
- 待提交收据是可靠投递所需的最小状态，不能替代 acpx 聊天存储；已经写入 acpx 的正文不再保留在收据中。
- 内存视图缓存有数量上限，正在发送/控制或有不确定收据的条目不会被清除。

## 仍需继续治理

1. ~~IPC 仍广播完整快照，UI 每 900ms 拉取完整历史。~~ 已改为按卡片订阅加事件增量，见 [acp-sync-protocol.md](acp-sync-protocol.md)。历史分页仍未做：连接时依然发送完整会话，长对话的首次加载不能声称已具备大规模承载能力。
2. 协议在 Rust、Node、TypeScript 三处重复声明，部分仍用 any/Value。应建立版本化契约和统一的运行时输入/响应校验。
3. 快照中的旧 state 字段仍兼容牌堆工作/待查看分类；长期需要独立的 connection、execution、pendingDecision 字段，逐步移除各层推导。
4. acpx 接入有针对固定版本源码的构建补丁。已有补丁锚点检查和回归测试，但升级仍需显式复核。
5. 目前验收覆盖隔离本地 fixture，不覆盖所有 Harness 的取消、断网、睡眠唤醒和 SSH 真实故障。也不提供跨系统副作用的 exactly-once 保证。

## 活跃卡片连接保活（2026-09-28）

- Rust 后台按机器管理所有未归档且已选 Harness 的卡片，不依赖聊天组件挂载或是否位于前台。空白、归档卡片不预热。
- 每台机器独立检查，启动并发为 2，启动后不因空闲或卡片切换释放连接；轻量 health 只返回连接与忙碌标记，不传完整历史。
- Agent 进程退出后清理失效句柄并恢复原绑定；失败按 10、20、40 秒等退避，最高 5 分钟。不自动重发旧消息。
- 自动启动与手动启动、UI/MCP 归档共享启动锁；启动结束再次校验卡片身份，过期清理必须匹配 connectionId。
- 验证：隔离 acpx fixture 覆盖多卡片无提示词预热、空闲保留、进程 SIGKILL 后恢复、并发恢复去重、旧连接清理不影响新连接。此改动未解决前台完整快照轮询及 Markdown 重渲染开销，也不代表所有 Harness 或真实 SSH 故障已验收。

## MCP 自动接通目标会话（2026-09-28）

- `read_session`、`send_message`、`subscribe_session`、`get_turn_status` 在检查运行授权前，自动接通原有未归档目标；后台正在启动时等待同一次启动。保留卡片、工作区和 Harness 身份校验。
- 接通发生在 MCP 全局工具锁之外；接通后重新检查发送方身份和授权，不能通过自动恢复绕过权限。连接状态与卡片可操作性分别返回，不再告诉 Agent 把暂时断连当作需要手工启动的冻结状态。
- 原生 HTTP API + 真实 acpx runtime + 隔离 fixture Agent 的无窗口端到端测试，覆盖关闭连接后直接发送并完成、重复 requestId 去重、过期发送方拒绝、归档目标不唤醒。测试不向用户真实卡片发送消息。
